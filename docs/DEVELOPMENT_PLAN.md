The target is the standalone Scene Rehearsal repository at `/Users/zaffran/vibed/scene-rehearsal`. It was absent before this planning run. There is no current application, dependency manifest, CI, test suite, or existing visual baseline. Kairo, Mesh Foundry and Scene Loom are separate checkouts.

## First complete workflow

Deliver one rehearsal from CLI publication to owner-approved portable handoff through the normal app. Use a fictional Kairo office with two researchers and two stations, a quiet scenario and an interruption scenario with a repeated alert and recovery. Use a reviewed test GLB and clip for one required slot, with intentionally designated primitives elsewhere. Use synthetic data throughout. This first workflow is a production-shaped increment in the full tool, with durable revisions and permissions.

| Scene IDs | Workflow and observable state |
| --- | --- |
| `build-plan`, `contract`, `library` | Agent publishes through CLI. Reviewer opens revision and scenario from library. Empty library, invalid publication, duplicate request, stale base and missing revision have explicit states. |
| `blockout`, `runtime`, `scenarios` | Reviewer plays, pauses, scrubs, steps, resets and orbits. Inspector describes quiet work, interruption, repeat-event decision and recovery. |
| `feedback`, `review-flow` | Reviewer saves a spatial or range note. Agent publishes a linked child revision. Reviewer compares both at the same time and resolves or reopens the note. |
| `assets`, `asset-flow` | Map exact accepted source revision and clip. Missing or invalid required assets block final approval while blockout inspection stays available. |
| `handoff`, `delivery` | Owner approves the exact revision. Export a verifiable package. Later edits create a fresh draft and preserve earlier approval history. |
| `kairo-consumer`, `release-checks` | Use a headless consumer conformance check in this slice. Subsequent Kairo integration runs the same scenarios and verifies the 70/30 layout and read-only evidence adapter in Kairo. |

Full delivery also covers backup and restore, larger asset libraries and the approved office running in Kairo. General-purpose editing, Blender authoring, cloud sync, and trading integrations are outside scope.

## Interface direction

Design a quiet desktop workbench. Give the viewport most of the space, put a shallow scenario timeline directly below, and keep one contextual inspector for the selected event, object, or note. Keep revision and approval state visible above the viewport. Reserve a strong accent for the playhead and selected target. Use labels and shapes with color for state. Below desktop width, stack the inspector below the viewport and keep playback in view. Provide a keyboard-selectable object/event list and accessible timeline controls so spatial feedback has an alternative to pointer picking.

DaVinci Resolve's current Edit page shows the value of keeping the viewer, timeline and selection inspector in context. The April 2025 guide's dated Edit page screenshots show the timeline/viewer relationship in actual use. Blender's 4.5 animation redesign documents the problem of timeline scrubbing fighting with selection. Use separate marker selection and time seeking here. The revision status, feedback restoration, and event-rule explanation are specific to this reviewer workflow. ## Architecture and contracts

- Use React and TypeScript with Vite, Three.js with GLTFLoader and orbit controls, and Radix Primitives for slider, select, tabs, dialog, tooltip and toolbar. Use native labeled buttons and forms for simple controls. Render the 3D canvas separately from semantic controls. Use stable revision and scenario URLs and retain library navigation on reload. [Vite](https://vite.dev/guide/) · [Three.js loader](https://threejs.org/docs/pages/GLTFLoader.html) · [Radix](https://www.radix-ui.com/primitives) · [Radix slider](https://www.radix-ui.com/primitives/docs/components/slider)
- Serve the built UI and versioned API through one local Fastify service. The CLI uses the same service. Use schema validation for input and domain validation for references. Keep a single SQLite database for revisions, notes, decisions and idempotency receipts, with SHA-256-addressed files beside it for GLBs. Prefer Node's SQLite API on a supported LTS line after verifying its stability on the selected version. Pin exact runtime and dependency versions in implementation after checking support, licenses and package compatibility. [Fastify validation](https://fastify.dev/docs/latest/Reference/Validation-and-Serialization/) · [Node SQLite](https://nodejs.org/api/sqlite.html) Use Node 24 LTS, with a minimum of 24.15 for the documented release-candidate SQLite API. Isolate that API behind the persistence module. Verify the chosen patch and dependency engines, peer ranges and licenses before locking versions. [Node 24 SQLite](https://nodejs.org/docs/latest-v24.x/api/sqlite.html) · [Vite requirements](https://vite.dev/guide/) · [Fastify v5 requirements](https://fastify.dev/docs/latest/Guides/Migration-Guide-V5/)
- Resolve an explicit absolute data directory at startup or use a documented local Application Support default. Show the effective path in a status command. Use database transactions to publish revisions with base-revision checks and retry receipts. Write validated blobs atomically before a transaction references them. Preserve parent revisions and feedback histories. Require verified blob hashes on import and export.
- Bind to loopback and reject foreign origins and invalid hosts. Use scoped credentials for author CLI requests. Review uses the local browser without enrollment. Accept revision records final approval for the exact digest with a single click. The browser automatically obtains an in-memory review token from the local service. Local clients can obtain the token, and review writes require it. Author credentials alone grant draft publication, feedback linking and verified model import.
- Use integer simulation ticks, stable ID ordering for simultaneous events, and seeded choices. Keep the evaluator free of renderer state, wall time, and Kairo dependencies. Seek by restoring initial state and replaying ordered ticks. Store units, axis conventions, station anchors, route segments, transitions, event rules and scenario expectations in the versioned manifest. First fixture merges repeated events from the same feed during response. Record the authored rule in the inspector. Never infer a production outage from a missing report.
- Save a pin with revision, scenario, tick or range, camera position and target, and either stable object ID with object-local point or world point. Restore original context. Comparison synchronizes scenario time and camera where possible. Keep pins anchored to their original revision when geometry changes.
- Mesh Foundry documents a project bundle export with metadata and owned file bytes. Import a user-selected bundle through a read-only adapter, verify the accepted stage/revision and GLB hash, validate the selected clip, and copy only mapped bytes. Check the actual bundle schema against an isolated export before locking the adapter. No live library writes. [Local Mesh Foundry interface](../../mesh-foundry/docs/agent-interface.md)
- Export a portable versioned manifest with relative blob paths, revision hash, approval record, paths, rules, scenarios, expected outcomes and asset provenance. The receiver checks integrity and fails closed on unsupported schemas, missing blobs or invalid paths. An exported hash checks byte integrity. Approval authority comes from the owner review record. Distinguish blockout sign-off from final implementation approval in storage and the manifest. Canonically encode the manifest and bind every blob by path and SHA-256. At final export, display the manifest digest in the owner session. The owner confirms that digest separately from the package, and the consumer records it in its own trusted configuration. The consumer compares the digest against that configuration, requires final implementation approval and checks schema, paths and blobs before loading. Importing a package never adds an entry to the trust configuration.

## Verification and implementation order

1. Establish the schema and deterministic evaluator. Verify fixed-tick outcomes, event ordering and repeat handling, and equivalence of forward playback, step, seek and reset.
2. Build the normal service startup, isolated datastore and CLI. Verify resolved datastore path, clean and restart behavior, invalid input rollback, concurrent stale publication, idempotent retry, role checks and asset hash validation. Verify that requests with author credentials cannot approve revisions or resolve feedback, and that foreign origins are rejected.
3. Run browser acceptance against the normal built app and real local service with an isolated data directory. Publish through the CLI, open the revision, change scenario, replay, save and reopen a pin, publish and compare a child, approve it and export. Assert keyboard scrub and marker selection, focus return after dialogs, 1440px and 1024px layouts and stacked inspection at 390px. Reload and restart, then reopen the same note and verify camera, tick and selection. Check accessible feedback for missing assets and unavailable WebGL. Test browser back and forward between library and revision, a direct link to a missing revision, and saving and reopening a time-range note using the keyboard.
4. Use an isolated Mesh Foundry library with a test-only accepted GLB to verify the real bundle round trip, mapped clip playback and offline reopen. Tamper with an export and verify rejection. Run the exported behavior fixture through a consumer harness and match expected state at specified ticks. Check application and browser tests before handing the revision to Kairo. Test rejection of a package with changed content and recomputed manifest and blob hashes, and of a blockout-only package even if its digest is allowlisted. Verify the separately confirmed final digest succeeds.
5. In the subsequent Kairo implementation, validate quiet routines, interruption, repeat and recovery, click-to-inspect agreement, degraded evidence, responsive layout and frontend performance. Use recorded fixtures first. Preserve collector and governance boundaries. Track release evidence in Scene Loom when authorized.

## Implementation notes

Use React Router for the shared shell and revision/scenario URLs. Split the Three.js viewport from the route bundle. Use Khronos glTF Validator during Mesh Foundry import in addition to matching the exported hash and clip. The tested adapter consumes the documented mesh-foundry-1 project bundle with accepted model pointers and base64 GLB bytes. The first library holds one rehearsal and its revision history. The normal startup seeds a blockout only when the revision store is empty.

## Full delivery and release acceptance

The Kairo rehearsal remains a benchmark. Finish its asset-backed owner review and verified export before implementing the approved rehearsal in Kairo. Treat missing accepted assets and the owner's approval as gates on that benchmark.

For general use, support a rehearsal with a different actor and station layout, and connect Scene Loom and Mesh Foundry's copy-ready prompts to the Scene Rehearsal authoring workflow. Keep Kairo references out of the default prompts and onboarding. Retain the benchmark as an optional regression fixture.

After the implementation slices, run a fresh end-to-end acceptance test. Start from a new, unrelated Scene Loom project and its actual Copy prompt button, then paste the prompts into a fresh agent session. Follow the relevant Mesh Foundry prompt and owner acceptance steps, publish the rehearsal through its normal entry point, and complete owner review and verified export. Use only the copied prompts and the records they reference. A successful Kairo run does not satisfy this release check.
